# One Four Seven

A single-player, realistic snooker game for KaiC's iPhone 17 Pro Max, built and tested on
Windows first. The design is `docs/superpowers/specs/2026-11-01-one-four-seven-design.md`
(the spec): read the sections a task touches before starting it. KaiC plays and judges;
he does not read code.

Every milestone (spec section 21) runs through the project skill `running-a-milestone`:
one plan KaiC approves, then parallel agents build, check, fix and ship.

## Rules

- Public repo: no secrets in code, logs or CI output. Never add analytics, ads or SDKs
  that phone home.
- `core/` is plain C++17 with no Godot types. Doubles and SI units (metres, seconds,
  kilograms, radians). No fast-math; `-ffp-contract=off` / `/fp:precise` stay on.
- Core coordinates (`core/include/ofs/table_geometry.hpp`): origin at the table centre,
  +x towards the black, +y to the left seen from baulk. Godot maps core (x, y) to
  `Vector3(-y, height, -x)`; `game/scripts/table_space.gd` owns that mapping.
- GDScript is statically typed. Logging goes through the `Log` autoload, C++ through
  `ofs::log`; every event and field is in `core/data/log_schema.json`.
- Every new failure path logs enough to diagnose it from one occurrence (spec 16.10).
- Tests never touch the network (devlink tests use a local server on 127.0.0.1).
- Assets are generated or CC0, each listed in `THIRD_PARTY.md`. The one exception is the bought
  table model (Studio-Lab "Snooker Table", Fab standard licence): its files live only in the
  gitignored `licensed/` (as bought) and `game/licensed/` (fitted by `tools/fit_table.py`) and are
  never committed, uploaded or pasted anywhere. Without them the game draws its own table.
- No test or agent run of the game may show a window or take the keyboard on KaiC's PC: start it
  with `python scripts/background.py <command>` or `python scripts/run_debug.py --background`
  (screenshot and state-dump runs do this by themselves). `--headless` runs need nothing.
- Comments: sparse, explaining why, never narrating. Match the file around you.
- Never reformat a whole existing file.
- Build files (`CMakeLists.txt` everywhere, `project.godot`, `export_presets.cfg`) change
  only in a milestone's contracts commit or by their named owner.

## Building

- Godot: `D:\Tools\Godot\Godot_v4.7.1-stable_win64_console.exe`.
- Native build: `cmake -S . -B build/windows -G "Visual Studio 18 2026" -A x64`, then
  `cmake --build build/windows --config Debug`. The extension lands in `game/bin/`.
- Core tests: `ctest --test-dir build/windows -C Debug`.
- Godot tests: `python scripts/sync_data.py`, then `godot --headless --path game --import`
  (once per fresh checkout), then `godot --headless --path game -s res://tests/run_tests.gd`.
- Everything at once: `python scripts/gate.py` (`--quick` for the edit loop).
- Build and run the debug game in one step: `python scripts/run_debug.py [-- game args]`.
- Playable Windows build: `python scripts/build_windows.py` (`--shortcut` adds a desktop
  shortcut).
- Phone link server: `uv run tools/devlink.py` (background; logs land in `logs/<date>/`).
  Without it, Windows logs stay in `%APPDATA%/Godot/app_userdata/One Four Seven/logs`; they
  upload the next time the link connects. Pass `-- --no-link` to keep a run off the link.

## Building and shipping

iOS app, developed on Windows with no Mac. GitHub Actions does everything:
`ios-compile.yml` builds the iOS extension, exports the Godot project, compiles and
screenshots on pushes that touch the game, extension, core or iOS scripts, and
`testflight.yml` signs and uploads when `scripts/testflight.py start` dispatches it. The full playbook, including every manual
step and known failures, is the global `ios-testflight` skill. Load it before touching
signing, `testflight.yml`, the export presets or the compile workflow.

Identity: Godot project `game/`, exported Xcode project `OneFourSeven`, bundle id
`com.kaichuan.onefourseven` (extensions: none). Repo `KaiC5504/OneFourSeven` (public).
App Store Connect name: `One Four Seven`, home-screen label `147`, Apple ID `6829495084`.

1. Work on `dev`. Push. Wait for the compile check: it proves the app builds, launches, loads
   the table and logs cleanly. Its simulator screenshot is not the phone's look (the simulator
   falls back to the Compatibility renderer on software OpenGL and shows magenta); check every
   screen you touched with a Windows screenshot (`python scripts/run_debug.py -- --screenshot=<path>`),
   which renders with the phone's Mobile renderer.
2. `git checkout main && git merge --ff-only dev && git push && git checkout dev`
3. `python scripts/testflight.py start`. Green means Apple has processed the build. After
   any change to `testflight.yml`, run `start --dry-run` first. Until an App Store profile
   exists for the bundle id (the first build), add `--create-signing`.
4. Report the TestFlight build number, what changed and test steps for the phone.

The owner has authorised commit, push and Actions runs without asking. Never start a
signed build before the compile check is green.

The Mac mini (`ssh mac`, set up 2026-11-12) is the fast loop to KaiC's iPhone; TestFlight stays
the release. Load the global `mac-mini` skill before changing anything there. `python scripts/mac.py
phone` builds the committed HEAD on the Mac (release; `--debug` for the debug export, `--launch`
to open it) and installs it on the iPhone over Wi-Fi in about 25 s once warm, replacing the
TestFlight install; `build` stops before the install. It runs headless in the Mac's hidden
`~/.mac-dev/onefourseven`, signed with the shared development certificate, no Apple ID. The phone
must be on the Mac's Wi-Fi. It stops before doing anything unless the Mac's sound is muted: our testing never
makes a sound there, and its volume is not ours to change. Use it for feel checks and anything the phone must show; a TestFlight
build only to ship. The Mac has no simulator path: Godot 4.7.1's simulator template is
x86_64-only and the Mac has no Rosetta.
